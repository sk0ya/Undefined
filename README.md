# 📋 要件定義ゲーム

社内研修・チームビルディング用のワークショップゲーム。
制限時間・秘密情報・イベント・そして最後の「実運用テスト」で、要件定義の本質——質問する、隠れた事情を引き出す、利害を調整する、例外を潰す、スコープを守る——を遊びながら体験します。

- 対象: 製造業・ITコンサルティング会社などでの研修・遊び
- 人数: プレイヤー2〜40人+ホスト(ファシリテーター)1人。開始時に**最大4人のルームへ均等に自動分割**され、ルーム対抗戦になります
- 環境: PCブラウザのみ。**インストール不要**、公開URLを開くだけ
- 所要時間: 30〜90分

## はじめかた

1. 公開Pagesを使う場合は、ホストが [`https://sk0ya.github.io/Undefined/#host`](https://sk0ya.github.io/Undefined/#host) を開く。ローカルでホストする場合は、先に「[開発](#開発)」の `npm run host` を実行して `http://localhost:5173/#host` を開く
2. 画面に**6文字のルームコード**が出るので、参加者に伝える(参加リンクをコピーして共有してもOK)
3. 参加者は同じURLを開き、コードと名前を入れて参加
4. 全員そろったらホストがシナリオを選んで「ゲーム開始」

ホストのタブがゲームの本体です。**開いたまま進行してください**(誤って閉じても、同じブラウザで開き直せば途中から再開できます。復帰時にはゲームコード・フェーズ・保存時刻を表示します)。ローカルでホストしている場合、参加者には公開Pages URLを案内してください。参加者の別PCからホストPCの `localhost` は開けません。

## 2つのゲームタイプ

**🎤 ヒアリング型**(おすすめ・シナリオ01)
プレイヤーは**開発チーム**(PM・開発・UX・業務分析)。ホスト(+AI)が演じるNPC(店長・ホールスタッフ・常連客・経理)にヒアリングし、**質問によって隠れ要件を発見**しながら仕様を確定します。NPCは「聞かれたことだけ」答えます。仕様確定後、AIが**実運用テスト**——「直後に電話で8名の予約が入る」「予約時間から20分経っても客が来ない」——をシミュレーションし、仕様の穴で事故を起こしにいきます。採点はシナリオ固有のルーブリック(シナリオ01は30/20/15/20/15の5軸、合計100点)+「質問王」「例外ハンター」などの称号、そして「3か月運用したら起きそうな問題3つ」。

質問はプレイヤーの画面から直接送れます。CodexブリッジまたはOpenAI互換APIを設定し、ホスト画面の**NPC自動回答をオン**にすると、AIがNPCになりきって即答します。オフなら、質問キューを見ながらホストが回答できます。AIが失敗した質問はキューに戻るため、手動回答へ切り替えられます。質問と回答はルーム全員に共有され、**採点時に「誰がどんな質問をしたか」まで含めてAIが判定**します——「質問王」の称号はここから決まります。

**🎭 ステークホルダー型**
プレイヤーは**クライアント企業のステークホルダー**(製造部長・経営企画など)。各自が**秘密の勝利条件**(「〜を要件に入れさせる/入れさせない」)を持ち、協力しつつ暗躍しながら要件定義書を作ります。露骨に主張すると悟られ、黙っていると要件から漏れるジレンマが肝。

## 遊び方(ゲームの流れ)

| フェーズ | 内容 | 目安 |
|---|---|---|
| 1. ロビー | プレイヤーがルームコードで参加。ホストがシナリオを選択 | 5分 |
| 2. ブリーフィング | 各自が自分のロール(公開情報+**あなただけが知る情報・個人目標**)とシナリオを読む。チームの顔ぶれも確認できる | 5〜10分 |
| 3. ヒアリング・議論 | **画面からNPCに質問**しつつ議論し、「要求カード」を提出して**全員で仕様書を書く**。ホストは台本イベントで揺さぶる | 20〜30分 |
| 4. 合意形成(投票) | 各要求カードに賛成/反対を投票。多数決で仮決定、同数はホスト裁定 | 5〜10分 |
| 5. 仕上げ | 全員で要件定義書を仕上げ、ホストがAI採点(+実運用テスト)を実行 | 10分 |
| 6. 結果発表 | チームスコア、実運用テスト結果、隠れ要件の発見状況、個人目標の達成、称号、次回の一手を公開 | 10分 |

各フェーズでプレイヤーは**「準備OK」**を出せます。ホストの操作バーに `準備OK 3/4` と出るので、全員待たせる/置いていく事故が減ります(フェーズを進めると自動でリセット)。タイマーは残り1分と0秒で音が鳴り、進捗バーが減っていきます(🔊 でミュート可)。

仕様書は全員で同時編集できます。編集者表示・自動保存状態・競合時の「サーバー内容／自分の下書き」の選択があり、完成後はMarkdownのコピー・保存・印刷ができます。要求カードには議論中のリアクションも付けられます。

ホスト画面には、接続切れ・未回答質問・未投票・準備状態・停滞をもとにした**ルーム優先キュー**があります。ルームを巡回しながら、フェーズの直接移動、タイマー延長、因果チェーン、開始用読み上げ、停滞時のヒント、時間不足時の短縮ルートを使えます。結果発表では、得点だけでなく質問数・要求カード・採用数・仕様書の空欄数など、ルームごとの進め方も比較できます。

## マルチルーム(ルーム対抗戦)

- 参加者は全体ロビーに集まり(最大40人)、ホストが開始すると自動で均等なルームに分かれます(例: 10人 → 4人×1・3人×2)。ロールはルーム内でランダム配布
- フェーズ・タイマー・イベント配信はホストが**全ルーム一斉制御**。要求カード・仕様書・投票・採点は**ルームごとに独立**
- ホストコンソールはルームタブと優先キューで巡回でき、AI採点は選択中のルームに対して実行。結果発表では**ルーム対抗リーダーボード**(チームスコア順位)と、各ルームの議論量・採用数・仕様書の空欄比較が表示されます
- **欠員ロールの補償**: 2〜3人のルームでは、不在ロールの「本人だけが知る情報」が**引き継ぎ資料**としてそのルームに自動公開されます。情報格差でチームスコアが不利にならず、不在ロールの個人目標は採点対象外です
- 途中参加者は空きのあるルームへ自動配属されます

## 公開のしかた(GitHub Pages)

このリポジトリをGitHubにpushし、**Settings → Pages → Source を「GitHub Actions」に設定**するだけです。
`main` への push、またはActionsの手動実行で `.github/workflows/pages.yml` が走り、ゲームロジックのテスト → シナリオのstrict検証 → Playwright/ChromiumのE2Eスモークテスト → ビルド → 公開まで自動で行われます。

配信パスはワークフローが自動判定します(`<name>.github.io` なら `/`、プロジェクトページなら `/<リポジトリ名>/`)。

## AI連携

AIは**任意**です。未設定でも全機能が遊べます(プロンプトをコピーしてChatGPTに貼り、返答を貼り戻す手動モード)。

### hostでCodexを使う(コピペ不要)

host PCにCodex CLIをインストールしてログインした状態で、リポジトリの `web` ディレクトリから次を実行します(ゲーム自体はCodexなしでも動きます):

```bash
npm install
npm run host
```

`npm run host` はゲーム画面(`http://localhost:5173`)とCodexブリッジ(`127.0.0.1:8787`)を同時に起動します。そのままホスト画面の「🔑 AI設定」で `Codex(host PC)` を選び、「接続確認」が成功すれば、採点・NPC回答・イベント生成・ファシリ補助を画面から直接Codexへ依頼できます。Codexは一時ディレクトリ・読み取り専用・120秒タイムアウトで実行します。停止は `Ctrl+C` です。5173番ポートを変更する場合は `REQGAME_HOST_PORT` を使います。

ローカルhost画面の参加リンクは、標準では `localhost` のURLです。同じPCの参加者はそのまま使えますが、別PCの参加者には公開Pages URL [`https://sk0ya.github.io/Undefined/`](https://sk0ya.github.io/Undefined/) に `#<コード>` を付けたURLを案内してください。ローカル画面のコピーリンクを公開URLにしたい場合は、`npm run host` の前に次を実行します:

```powershell
$env:VITE_PUBLIC_GAME_URL = "https://sk0ya.github.io/Undefined/"
npm run host
```

当日の進行手順は [host向け進行ガイド](docs/HOST_GUIDE.md) にまとめています。

GitHub Pagesの公開画面を使う場合も、ブリッジを実行している同じhost PCのブラウザでゲームを開いてください。公開Originを限定する場合(PowerShell)は、`$env:REQGAME_CODEX_ORIGIN = "https://sk0ya.github.io"` を設定してから `npm run codex:bridge` を起動します。公開画面ではローカルのViteは不要です。ブリッジを起動できない場合は、従来のOpenAI互換APIまたは手動モードへ切り替えられます。

ホスト画面の「🔑 AI設定」で `OpenAI互換API` を選んでAPIキーを入れると、自動モードになります。Codexを使う場合は、上のローカルブリッジ方式を選べます:

- **🏅 AI採点** — 最終成果物の品質(シナリオごとのルーブリック、既定は4軸×25点)、各プレイヤーの個人目標、隠れ要件の発見状況、実運用テスト、称号、将来問題までまとめて判定。**ヒアリング記録(誰が何を質問したか)も判定材料に含まれます**
- **🎤 NPC回答** — プレイヤーの質問にAIがNPC(店長など)になりきって「聞かれたことだけ」答える。NPC自動回答をオンにした場合だけ自動で即答し、ホストの「質問キュー」には未回答分だけが残ります。自動回答はトグルでオフにでき、AIが失敗した質問はキューに戻るのでホストが手で答えられます
- **🌀 揺さぶりイベント生成** — 「社長の鶴の一声」など議論の前提を変える追加情報を生成し、全員に配信
- **💡 ファシリ補助** — 議論の抜け漏れや投げかけるべき質問を提案(ホストにのみ表示)。シナリオ同梱の因果チェーン・読み上げ・ヒント・短縮ルートもホスト専用に表示

要件定義書は画面からMarkdownをコピーまたは`.md`ファイルとして保存でき、紙で配る場合は印刷できます。

**キーの扱い**: キーは**ホスト本人のブラウザにだけ**保存され、そこからAPIへ直接送られます。ゲームの状態にもプレイヤーへの配信内容にも一切含まれません。共用PCでは「このブラウザに保存する」のチェックを外すと、タブを閉じたときに消えます。ブラウザから直接呼ぶため、APIがCORSを許可している必要があります(OpenAIは対応)。

## アーキテクチャ

サーバーはありません。**ホストのブラウザがゲームの権威**になり、プレイヤーはWebRTCのデータチャネルで直接そこに繋ぎます。

```
┌─ ホストのブラウザ(ゲーム本体) ───────────┐
│  GameEngine       … 状態・フェーズ・採点     │
│  HostSession      … 接続受付・スナップショット配信 │
│  localStorage     … 進行中ゲームの保存(復帰用) │
│  AI呼び出し        … CodexブリッジまたはAPIへ    │
└──────────┬────────────────────────────────┘
     WebRTC DataChannel(スター型)
     ├── プレイヤー1
     ├── プレイヤー2
     └── …(最大40人)
```

- **秘密の保護**: 状態はホストが一元管理し、変更のたびに**閲覧者ごとにフィルタしたスナップショット**を配ります。他人の個人目標・NPCの手の内・他ルームの中身は、そもそも送られません(`buildSnapshot`)
- **接続**: 相手を見つける手順(シグナリング)だけPeerJSの公開ブローカーを借り、確立後の通信は端末同士で直接流れます。同一LAN内ならローカル経路で繋がります
- **復帰**: プレイヤーはトークンで識別され、リロード・再接続しても同じロールに戻ります。ホストもリロードで同じルームコード・同じ進行状況に復帰します
- **タイマー**: ホストの時計を基準に同期します

### 制約

- **インターネット接続が必要です**(ページの配信と、相手を見つけるシグナリングのため)。完全オフラインのLANでは動きません
- **WebRTCを遮断するネットワークでは繋がりません**。社内プロキシ・ファイアウォールが厳しい場合は、別回線やテザリングで試してください
- ホストのタブを閉じるとゲームは止まります(同じブラウザで開き直せば復帰できます)

## 開発

必要なもの: Node.js 20+

```powershell
cd web
npm install
npm run dev                        # http://localhost:5173/ (/#hostでホスト画面)
npm run host                       # ViteとCodexブリッジを同時起動(ローカルhost向け)
npm test                           # ゲームロジック・AIプロンプトのテスト
npm run validate:scenarios         # シナリオ定義の検証
npm run validate:scenarios:strict  # CIと同じ厳格な検証
npm run build                      # dist/に静的ファイルを出力
npm run preview                    # dist/をローカル配信
npm run test:e2e                   # Chromiumでhost/プレイヤーの主要フローを確認
```

ブラウザテストを初めて実行する場合は、先に `npx playwright install chromium` を実行してください。GitHub Actionsでは依存関係付きのChromiumをインストールしてからE2Eを実行します。

CIでは `npm ci`、`npm test`、`npm run validate:scenarios:strict`、Playwright/ChromiumのE2E、`npm run build` を順に実行します。

構成:

- `web/src/game/engine.ts` — ゲームの権威ある状態と全ロジック。**スナップショットのフィルタがゲームの根幹**なので、変更は慎重に
- `web/src/game/protocol.ts` — プレイヤーからのメッセージとその適用
- `web/src/game/scenarios.ts` — `scenarios/*.json` の取り込み
- `web/src/net/peer.ts` — WebRTC接続層(ホスト側・プレイヤー側)
- `web/src/ai/` — プロンプト生成とAPI呼び出し
- `web/src/` — React画面(`PlayerApp` / `HostApp` / `components`)
- `web/test/engine.test.ts` — ロジックのテスト。**秘密が漏れないことの検証を含む**
- `web/test/ai.test.ts` — AIプロンプトとレスポンス解析のテスト
- `web/e2e/game-flow.spec.ts` — 参加から結果発表、復帰、仕様書競合、AIフォールバック、複数ルームのE2E
- `scenarios/` — シナリオ定義JSON

## シナリオの自作

`scenarios/` の既存JSONをコピーして編集してください。要点:

- `type` — `"hearing"`(ヒアリング型)または省略(ステークホルダー型)
- `roles[].secretConditions[]` — 個人目標/秘密の勝利条件。`judgeHint` にAIが達成判定するための基準を書く
- ロールは4つ定義し、2〜3人プレイでは一部のロールだけがランダムに配布されても成立するように、条件同士を対立・交差させると面白くなります
- ヒアリング型の追加フィールド(すべて任意):
  - `npcs[]` — ヒアリング対象。`knowledge[]` に情報と `revealWhen`(開示条件)を書く。プレイヤーには名前と冒頭の発言のみ見える
  - `hiddenRequirements[]` — 質問で発見すべき隠れ要件(R1, R2, …)。採点時にAIが発見状況を判定
  - `scriptedEvents[]` — 「残り15分」などのタイミング付きイベント台本。ホストがワンクリックで配信
  - `testCases[]` — 実運用テストケース。採点時にAIが仕様に対してシミュレーション
  - `rubric[]` — 採点ルーブリック(名称・配点・内訳)。省略時は既定の4軸×25点
  - `titles[]` — ボーナス称号の定義(質問王など)。AIが最もふさわしいプレイヤーに授与
- `eventIdeas` — ホスト用の揺さぶりイベントのネタ帳(AI生成の種にもなる)
- `difficulty` / `recommendedPlayers` / `recommendedMinutes` — シナリオ選択画面に表示する目安
- `facilitation` — 開始時の読み上げ、停滞時の3段階ヒント、時間不足時の短縮ルート
- `beats` — 事件の発生条件・影響・問い・未対応時の結果からなる因果チェーン。ホスト表示と採点プロンプトに使われる

追加したシナリオは、次のコマンドで取り込み前に検証できます。

```powershell
cd web
npm run validate:scenarios:strict
```

良いシナリオの作り方は「シナリオ=正解の仕様書」ではなく「**世界の設定+登場人物の事情+制約+起こりうる事件**」。最初は簡単そうに見えて、良い質問をすれば掘り当てられる深さを仕込むのがコツです。
