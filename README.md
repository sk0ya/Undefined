# 📋 要件定義ゲーム

社内研修・チームビルディング用のワークショップゲーム。
制限時間・秘密情報・イベント・そして最後の「実運用テスト」で、要件定義の本質——質問する、隠れた事情を引き出す、利害を調整する、例外を潰す、スコープを守る——を遊びながら体験します。

- 対象: 製造業・ITコンサルティング会社などでの研修・遊び
- 人数: プレイヤー2〜40人+ホスト(ファシリテーター)1人。開始時に**2〜4人のルームへ自動分割**され、ルーム対抗戦になります
- 環境: 同一LAN内のPCブラウザ(ホストPCがサーバーを兼ねる)
- 所要時間: 30〜90分

## 2つのゲームタイプ

**🎤 ヒアリング型**(おすすめ・シナリオ01)
プレイヤーは**開発チーム**(PM・開発・UX・業務分析)。ホスト(+AI)が演じるNPC(店長・ホールスタッフ・常連客・経理)にヒアリングし、**質問によって隠れ要件を発見**しながら仕様を確定します。NPCは「聞かれたことだけ」答えます。仕様確定後、AIが**実運用テスト**——「直後に電話で8名の予約が入る」「予約時間から20分経っても客が来ない」——をシミュレーションし、仕様の穴で事故を起こしにいきます。採点は 基本要件40/例外ケース25/要求品質20/プロジェクト判断15 の100点満点+「質問王」「例外ハンター」などの称号、そして「3か月運用したら起きそうな問題3つ」。

**🎭 ステークホルダー型**
プレイヤーは**クライアント企業のステークホルダー**(製造部長・経営企画など)。各自が**秘密の勝利条件**(「〜を要件に入れさせる/入れさせない」)を持ち、協力しつつ暗躍しながら要件定義書を作ります。露骨に主張すると悟られ、黙っていると要件から漏れるジレンマが肝。

## 遊び方(ゲームの流れ)

| フェーズ | 内容 | 目安 |
|---|---|---|
| 1. ロビー | プレイヤーがLAN内URLから参加。ホストがシナリオを選択 | 5分 |
| 2. ブリーフィング | 各自が自分のロール(公開情報+**あなただけが知る情報・個人目標**)とシナリオを読む | 5〜10分 |
| 3. ヒアリング・議論 | NPCへのヒアリング(口頭)や議論をしつつ、「要求カード」を提出し、**全員で仕様書を書く**。ホストは台本イベントで揺さぶる | 20〜30分 |
| 4. 合意形成(投票) | 各要求カードに賛成/反対を投票。多数決で仮決定、同数はホスト裁定 | 5〜10分 |
| 5. 仕上げ | 全員で要件定義書を仕上げ、ホストがAI採点(+実運用テスト)を実行 | 10分 |
| 6. 結果発表 | チームスコア、実運用テスト結果、隠れ要件の発見状況、個人目標の達成、称号を公開 | 10分 |

## マルチルーム(ルーム対抗戦)

- 参加者は全体ロビーに集まり(最大40人)、ホストが開始すると自動で均等なルームに分かれます(例: 10人 → 4人×1・3人×2)。ロールはルーム内でランダム配布
- フェーズ・タイマー・イベント配信はホストが**全ルーム一斉制御**。要求カード・仕様書・投票・採点は**ルームごとに独立**
- ホストコンソールはルームタブで巡回でき、AI採点は選択中のルームに対して実行。結果発表では**ルーム対抗リーダーボード**(チームスコア順位)が全員に表示されます
- **欠員ロールの補償**: 2〜3人のルームでは、不在ロールの「本人だけが知る情報」が**引き継ぎ資料**としてそのルームに自動公開されます。情報格差でチームスコアが不利にならず、不在ロールの個人目標は採点対象外です
- 途中参加者は空きのあるルームへ自動配属されます

シナリオは `scenarios/*.json` に定義。**実行ファイルと同じ場所に `scenarios/` フォルダを置けば、ビルドせずにシナリオを追加・上書きできます**(同じidは上書き)。

## セットアップ

必要なもの: Go 1.24+、Node.js 20+(ビルド時のみ)

```powershell
.\build.ps1        # web をビルドして reqgame.exe を生成
.\reqgame.exe      # サーバー起動
```

起動するとLAN内のURLが表示されます:

```
プレイヤー用URL:  http://192.168.x.x:8080/
ホスト用URL:      http://192.168.x.x:8080/host
```

プレイヤーはスマホ不要、PCブラウザで参加します(ホストPCのファイアウォールでポート8080の受信許可が必要な場合があります)。

### 環境変数

| 変数 | 説明 | 既定値 |
|---|---|---|
| `PORT` | リッスンポート | `8080` |
| `HOST_KEY` | ホスト画面/AI APIの合言葉。未設定なら誰でもホスト可 | (なし) |
| `AI_API_KEY` | OpenAI互換APIキー(`OPENAI_API_KEY`でも可)。未設定なら手動モード | (なし) |
| `AI_BASE_URL` | OpenAI互換APIのベースURL | `https://api.openai.com/v1` |
| `AI_MODEL` | モデル名 | `gpt-5-mini` |

## AI連携(ChatGPT / Codex)

ホストコンソールから4種類の指示が出せます:

- **🏅 AI採点** — 最終成果物の品質(シナリオごとのルーブリック、既定は4軸×25点)、各プレイヤーの個人目標、隠れ要件の発見状況、実運用テスト、称号、将来問題までまとめて判定
- **🎤 NPC回答** — プレイヤーの質問を入力すると、AIがNPC(店長など)になりきって「聞かれたことだけ」答える(ヒアリング型)
- **🌀 揺さぶりイベント生成** — 「社長の鶴の一声」など議論の前提を変える追加情報を生成し、全員に配信
- **💡 ファシリ補助** — 議論の抜け漏れや投げかけるべき質問を提案(ホストにのみ表示)

動作モードは2つ:

1. **自動モード** — `AI_API_KEY` を設定すると、サーバーがOpenAI互換APIを直接呼び、結果を即ゲームに反映
2. **手動モード**(既定)— サーバーが生成した完全なプロンプトをコピーし、ホストが手元の **ChatGPT / Codex** に貼り付け、返ってきたJSONを貼り戻して反映。**インターネット接続がホストの手元にしかない環境でも運用できます**

## アーキテクチャ

```
┌─ ホストPC ──────────────────────────────┐
│  reqgame.exe (Go, 単一バイナリ)          │
│   ├ WebSocketハブ (/ws)  ← 状態同期      │
│   ├ React配信 (embed)                    │
│   ├ シナリオ管理 (embed + scenarios/)    │
│   └ AIプロキシ (/api/ai) ─→ OpenAI互換API │
└──────────┬───────────────────────────────┘
   LAN (WebSocket)
   ├── プレイヤー1〜4 (ブラウザ: /)
   └── ホストコンソール (ブラウザ: /host)
```

- 状態はサーバーがメモリ上で一元管理し、変更のたびに**閲覧者ごとにフィルタしたスナップショット**を全クライアントへ配信(自分以外の秘密条件は結果発表まで見えない)
- プレイヤーはトークンで識別され、リロード・再接続しても同じロールに復帰
- タイマーはサーバー時刻基準で同期

## 開発

```powershell
# ターミナル1: Goサーバー (要 web/dist — 初回は build.ps1 を実行)
go run .

# ターミナル2: フロント開発サーバー (http://localhost:5173、/ws と /api は :8080 にプロキシ)
cd web; npm run dev
```

構成:

- `main.go` — HTTPサーバー、静的配信、AIエンドポイント
- `internal/game/` — ゲーム状態・フェーズ管理・WebSocketハブ・スナップショット
- `internal/ai/` — 採点/イベント/補助のプロンプト生成、OpenAI互換クライアント、応答パース
- `scenarios/` — シナリオ定義JSON
- `web/` — React + Vite + TypeScript(`/` プレイヤー画面、`/host` ホストコンソール)

## シナリオの自作

`scenarios/` の既存JSONをコピーして編集してください。要点:

- `type` — `"hearing"`(ヒアリング型)または省略(ステークホルダー型)
- `roles[].secretConditions[]` — 個人目標/秘密の勝利条件。`judgeHint` にAIが達成判定するための基準を書く
- ロールは4つ定義し、2〜3人プレイでは一部のロールだけがランダムに配布されても成立するように、条件同士を対立・交差させると面白くなります
- ヒアリング型の追加フィールド(すべて任意):
  - `npcs[]` — ヒアリング対象。`knowledge[]` に情報と `revealWhen`(開示条件)を書く。プレイヤーには名前と冒頭の発言のみ見える
  - `hiddenRequirements[]` — 質問で発見すべき隠れ要件(R1, R2, …)。採点時にAIが発見状況を判定
  - `scriptedEvents[]` — 「残り15分」などのタイミング付きイベント台本。ホストがワンクリックで配信
  - `testCases[]` — 実運用テストケース。採点時にAIが仕様に対してシミュレーション
  - `rubric[]` — 採点ルーブリック(名称・配点・内訳)。省略時は既定の4軸×25点
  - `titles[]` — ボーナス称号の定義(質問王など)。AIが最もふさわしいプレイヤーに授与
- `eventIdeas` — ホスト用の揺さぶりイベントのネタ帳(AI生成の種にもなる)

良いシナリオの作り方は「シナリオ=正解の仕様書」ではなく「**世界の設定+登場人物の事情+制約+起こりうる事件**」。最初は簡単そうに見えて、良い質問をすれば掘り当てられる深さを仕込むのがコツです。
