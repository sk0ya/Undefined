# 要件定義ゲーム 完成度向上計画

最終更新: 2026-09-02

## 1. 目的

このゲームを、機能が多いゲームから「研修の場で迷わず進行でき、議論が自然に深まり、終了後に学びが残るゲーム」へ引き上げる。

改善の判断基準は次の3つとする。

1. **ユーザー体験**: プレイヤーが今やること・次にやることを迷わない
2. **hostの操作性**: hostが複数ルーム、タイマー、質問、イベント、採点を安全に捌ける
3. **シナリオの面白さ**: 質問・対立・制約・事件がつながり、チームごとに違う判断が生まれる

## 2. 現状認識

### 2.1 すでにできていること

- ロビーから結果発表までの6フェーズ、準備OK、タイマー、ルーム対抗戦が実装済み
- hostはルームタブを切り替え、要求カード・質問・仕様書・採点結果をルーム単位で確認できる
- ヒアリング型では、AI自動回答とhost手動回答を切り替えられる。AI失敗時は質問キューへ戻る
- hostのリロード復帰、プレイヤーのトークン復帰、閲覧者ごとのスナップショットフィルタがある
- プレイヤーには他人の秘密情報・NPCの知識・他ルームの内容を渡さないテストがある
- 現時点の品質ベースラインは、ゲームロジックのテスト51件成功、本番ビルド成功
- hostはCodex CLIのローカルブリッジを使い、APIキーやAI回答のコピペなしで採点・NPC回答・イベント・ファシリ補助を実行できる

### 2.2 体験上の主な課題

#### プレイヤー側

- 議論フェーズの主要機能が「ヒアリング」「要求カード」「仕様書」などのタブに分かれ、最初に表示される内容以外が埋もれやすい
- フェーズごとの目的は表示されるが、「このフェーズで最低限やること」「完了条件」「次に見るべき場所」が一つのチェックリストになっていない
- 仕様書は同じ欄を同時編集すると上書きされる。編集中表示はあるが、競合を避ける操作ルールが画面上で弱い
- 接続中・回答待ち・自分の未投票など、待ち状態の理由が複数箇所に分散している
- 入力欄はプレースホルダー中心のため、アクセシビリティと入力ミス時の理解に改善余地がある

#### host側

- 現在のhost画面は、進行操作、ルーム巡回、質問キュー、NPC回答、イベント、AI設定、採点、ロール秘密を一画面に並べている
- ルームタブには人数・準備OK・未回答質問・得点は出るが、「今対応すべきルーム」の優先順位までは出ない
- フェーズ移動はステッパーから直接ジャンプできるため便利な反面、投票未完了・未回答質問・採点未実施を見落としやすい
- タイマー操作は使えるが、フェーズごとの推奨時間や「開始前」「一時停止中」「時間切れ」の運用判断がhostに委ねられている
- AIの実行、手動貼り付け、失敗時の再試行は存在するが、処理中・失敗・適用済みの状態を一貫した操作ログとして確認しにくい
- ブラウザ操作を通したE2Eテストがなく、実際のhost/プレイヤーの画面遷移はロジックテストほど守られていない

#### シナリオ側

- `restaurant` は、3つの台本イベント、10個の隠れ要件、7つの実運用テストを持ち、質問から事故までの流れが比較的厚い
- `smart-factory`、`kintai`、`supermarket` は、各1イベント・1隠れ要件・1テストケースで、`eventIdeas`は5件ある。実際のプレイ中に起きる展開の密度に差がある
- 役割の秘密条件は豊富だが、秘密条件、台本イベント、投票、実運用テストの因果関係がデータ構造上は緩く、シナリオ作成者が一貫性を確認しにくい
- 事件は時間起点が中心で、チームが特定の判断をした結果として状況が変わる設計を追加できる余地がある

## 3. プロダクト方針

### 方針A: 常に「次の一手」を見せる

各画面に、現在の目的、推奨アクション、完了条件、未対応件数を表示する。情報量は減らすのではなく、優先度順に並べ、詳細は展開できるようにする。

### 方針B: hostは監督、プレイヤーは意思決定者

hostには全体の異常・詰まり・未処理を集約し、プレイヤーには自分のルームの議論と判断に集中できる情報だけを出す。秘密情報の境界は変更しない。

### 方針C: 事件は「驚き」ではなく「判断の結果」を生む

イベントはランダムな横槍ではなく、公開情報・質問・採用した要求・明記した運用ルールと接続する。結果発表では、どの判断がどの事故を防いだかを説明できるようにする。

### 方針D: AIは加速装置であり、必須ルールにしない

AIがなくても同じゲーム体験が成立する。AIを使う場合も、処理中・失敗・手動引き継ぎを常に明示し、API障害で進行が止まらないようにする。

## 4. 優先順位付き改善項目

### P0-1: プレイヤーのフェーズガイドと行動チェックリスト

各フェーズの冒頭に、次の内容を固定表示する。

- このフェーズの目的
- チームで必ず行うこと
- できれば行うこと
- 完了条件
- 未完了件数（未回答質問、未投票カード、未記入セクションなど）
- 「準備OK」を押すと何が起きるか

議論フェーズの例:

1. NPCまたは仲間から事実を3つ聞く
2. 正常系だけでなく例外を1つ質問する
3. 要求カードを出す
4. 採用したい内容を仕様書に反映する
5. チーム全員が確認して準備OK

タブを残す場合でも、バッジを「件数」だけでなく「未対応」「新着」「自分の担当」に分ける。特にヒアリング型では、質問・要求カード・仕様書の入口を同時に見せるコンパクトなワークスペースを優先する。

### P0-2: host用「進行コックピット」

既存の機能を廃止せず、上部に次のサマリーを追加する。

- 現在のフェーズと残り時間
- 全体の参加者・接続中人数
- ルームごとの準備OK / 未投票 / 未回答質問 / 未採点
- 今すぐ対応すべき項目の優先キュー
- 次のフェーズへ進む前の確認事項

ルームタブは、単なる切り替えではなく「監視レーン」とする。優先度は次の順で表示する。

1. 接続切れ・未回答質問など、進行を止めるもの
2. 準備OKが揃ったルーム
3. 反応が少なく停滞しているルーム
4. 通常状態のルーム

フェーズジャンプは残しつつ、ジャンプ先と影響（タイマークリア、準備OKリセット、投票確定など）を確認画面で表示する。通常進行は「次のフェーズへ」を主導線にする。

### P0-3: タイマー・AI・復旧操作の一貫性

実装済み: AIの処理状態・失敗時フォールバックに加え、Codex CLIをhost PCから呼ぶローカルブリッジを追加した。ブリッジは読み取り専用・127.0.0.1待ち受けで、画面からの接続確認と手動モードへの切り替えを提供する。

- フェーズごとに推奨時間プリセットを持たせる
- 「開始」「一時停止」「再開」「リセット」を状態に応じて主ボタン1つへ整理する
- 時間切れ時は、音・表示・host向けの次の選択肢（延長 / 次へ / 継続）を出す
- AIは「待機中 / 実行中 / 適用済み / 失敗 / 手動対応済み」を表示する
- AI失敗時はエラーメッセージ、再試行、プロンプトコピー、手動回答を同じカードに置く
- リロード復帰時は、復帰したゲームコード・フェーズ・保存時刻を一度表示する

### P0-4: 仕様書編集の安全性

- 各セクションに「担当」「保存済み時刻」「自分が編集中」を表示する
- 他人が編集を開始した欄は、入力前に警告する
- 自動保存の成功 / 失敗を表示する
- 同時編集時の上書きは、可能であれば直前内容との差分確認を挟む
- hostの編集対象ルームをヘッダーにも常時表示する

初期実装では完全な共同編集基盤を導入せず、上書き事故を見つけやすくする表示と確認を優先する。

### P1-1: シナリオを「因果チェーン」で定義する

既存の `scriptedEvents` を置き換えず、後方互換のまま任意フィールドを追加する。

```text
公開状況 → 質問で得られる情報 → 役割間の対立 → チームの判断
       → 発生条件を満たした事件 → 運用上の結果 → 振り返り
```

追加候補のデータ項目:

- `beats`: シナリオの場面一覧（導入 / 探索 / 圧力 / 決断 / 結果）
- `trigger`: 時間、採用カード、未定義のまま残った論点などの発生条件
- `impact`: 仕様・運用・予算・納期への影響
- `facilitatorCue`: hostが投げる一言と、深掘り質問
- `counterfactual`: 要件に入っていた場合 / 入っていなかった場合の差

イベントを増やすだけでなく、同じ事件に対して複数の解決策が成立するようにする。正解を一つに固定せず、トレードオフを採点対象にする。

### P1-2: シナリオ間の厚みを揃える

`restaurant` をヒアリング型の基準シナリオとし、ステークホルダー型3本を次の最低ラインへ引き上げる。

- 役割間の対立軸: 3本以上
- イベント: 3本以上（導入後の圧力、スコープ揺さぶり、運用事故）
- 隠れ要件: 5本以上
- 実運用テスト: 5本以上（正常系1、境界・例外3、スコープまたは移行1）
- `eventIdeas`: hostが選びやすい発生条件・狙い・難易度を持つ

シナリオごとに、開始前の難易度（初級 / 標準 / 上級）と推奨人数・推奨時間も定義する。

### P1-3: 振り返りをゲーム体験に組み込む

結果発表に次を追加する。

- 得点だけでなく、どの質問・要求・判断が得点に寄与したか
- 見落とした要件について「本来どの相手に何を聞けたか」
- 実運用テストで起きた事故と、仕様書のどの空欄が原因だったか
- 各プレイヤーの個人目標と、チームの合意形成への影響
- チームが次回に一つだけ変える行動

ルーム対抗戦は順位だけで終わらせず、異なるルームが同じ事件にどう対応したかを比較できるようにする。

### P1-4: host向けファシリテーション支援

- 開始前の読み上げ台本（30秒版 / 2分版）
- プレイヤーが止まったときのヒントを3段階で提示
- hostがイベントを出す前に「今出す狙い」と「想定される議論」を表示
- 時間不足時の短縮ルート（質問を絞る、投票を省略する、採点だけ実施）
- AIなしで進行するためのNPC回答例と採点用プロンプトの導線

## 5. 実装フェーズ

### Phase 0: 計測可能な土台（1スプリント）

- 現行の表示・権限・秘密フィルタを固定する回帰テストを追加
- 各フェーズの代表的なSnapshot fixtureを作る
- ブラウザで「参加 → 開始 → 議論 → 投票 → 結果」のスモークテストを追加
- シナリオJSONの検証スクリプトを追加する
  - ロール数、秘密条件、参照先ID、イベントID、テストケースID
  - ステークホルダー型の最低コンテンツ量
- 計測はまず録画・観察・アンケートを中心とし、個人情報を含む外部分析基盤は導入しない

### Phase 1: P0のhost改善（1〜2スプリント）

- 進行コックピットとルーム優先度表示
- フェーズジャンプの確認と次フェーズ前チェック
- タイマー状態整理、時間切れフロー
- AI処理状態と手動フォールバックの統一
- 復帰・接続状態の表示改善

### Phase 2: P0のプレイヤー改善（1〜2スプリント）

- フェーズガイド、行動チェックリスト
- 未対応 / 新着バッジ
- 議論フェーズの主要導線を一画面に集約
- 仕様書の保存状態・編集競合表示
- ラベル、キーボード操作、フォーカス、色以外の状態表現を整備

### Phase 3: P1のシナリオ・学習改善（2スプリント）

- `beats` / `trigger` / `impact` の追加と後方互換読み込み
- 3つのステークホルダー型シナリオを最低ラインまで拡充
- 結果発表の因果説明とチーム比較
- host向け台本・ヒント・短縮ルート

### Phase 4: 磨き込み（1スプリント）

- 研修環境でのユーザビリティテスト
- 画面幅、低速回線、AIなし、途中切断、hostリロードの確認
- 文言、余白、音、アニメーション、印刷・Markdown出力の調整
- READMEとhost向け進行ガイドの更新

## 6. 受け入れ基準

### UX

- 初回プレイヤーが、参加後60秒以内に「自分の役割」と「最初にすること」を説明できる
- 各フェーズで、未対応の重要タスクが1画面で分かる
- モバイル幅または狭いノートPCでも、主要操作が横スクロールなしで実行できる
- AIなしでも、質問・議論・仕様書・投票・結果発表が完走できる

### host

- 10ルーム相当の状態で、対応が必要なルームを5秒以内に特定できる
- 次のフェーズへ進む前に、未準備・未投票・未回答・未採点の有無を確認できる
- AI失敗後、hostが10秒以内に手動対応または再試行へ移れる
- フェーズジャンプ、リセット、新しいルーム作成で、破壊的な影響を確認できる

### シナリオ

- 各シナリオに、正常系・例外・制約・対立・結果の5要素がある
- 事件は少なくとも1つ、プレイヤーの判断によって結果が変わる
- 結果画面で、見落としが「どの質問・判断の不足だったか」と結び付く
- 2〜3人の少人数でも、欠員ロールの引き継ぎだけで議論が成立する

### 品質・安全性

- 既存の秘密情報保護テストを維持し、追加フィールドも閲覧者別に検証する
- ロジックテスト全件成功、本番ビルド成功
- 主要ユーザーフローのブラウザスモークテスト成功
- 保存データのバージョンアップ時に旧データを壊さないか、復帰テストで確認する

## 7. 効果測定

外部テレメトリーは導入せず、まず各回のhost観察シートと終了後アンケートで測る。

- プレイヤーが最初の行動を始めるまでの時間
- hostが未対応ルームを見つけるまでの時間
- 「次に何をすればよいか分からなかった」回答率
- 質問数、例外に関する質問数、採用要求数、仕様書の未記入数
- AIなし / AIありでの進行停止回数
- 結果発表後に参加者が説明できる学びの数
- シナリオ別の盛り上がり、難しさ、納得感、再プレイ意向

最初の目標は、hostが途中で画面を探す時間を減らし、プレイヤーの「待ち時間」を減らすこと。スコア自体を上げることは副目標とし、質問や判断の質が上がった結果として評価する。

## 8. リスクと対策

| リスク | 対策 |
|---|---|
| host画面に情報を足しすぎて、かえって見づらくなる | 重要度順のサマリーを先に出し、詳細は展開式にする。ユーザーテストで確認する |
| イベントを増やしすぎて、hostが処理しきれない | 必須イベントと任意イベントを分け、短縮ルートを用意する |
| AIの回答がシナリオの秘密を先に漏らす | 既存のNPC知識フィルタ、回答プロンプト、回答後のhost確認を維持する |
| 共同編集改善で通信量・競合が複雑になる | まず表示・警告・保存状態を改善し、同期方式の刷新は後段にする |
| シナリオJSONの自由度が上がり、壊れたシナリオが増える | JSON検証とサンプルfixtureを先に追加する |

## 9. 今すぐ着手する最初のタスク

1. P0の画面仕様を、host用とプレイヤー用の2枚のワイヤーフレームにする

3. ルーム状態の優先度計算（接続切れ、未回答、未準備、停滞、通常）を純粋関数として実装・テストする
4. 既存4シナリオのコンテンツ量と因果チェーンを点検する
5. シナリオJSON検証のルールを追加する
6. 2〜4人の研修を想定したhost・プレイヤーのブラウザスモークテストを1本通す

### 今回の計画でやらないこと

- 初手からサーバー構成やWebRTC方式を変更すること
- AIを必須化すること
- スコア計算を、画面改善の検証前に大きく変更すること
- 外部分析サービスへ参加者データを送ること

まずは既存のゲームループを壊さず、見落とし・待ち・hostの判断負荷を減らす。そこから、シナリオの因果関係と振り返りを強化する。
